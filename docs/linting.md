# Linting

`zig-analyzer check` analyzes a directory tree and reports lint findings; the
same rules produce diagnostics and quick fixes in the language server.

```sh
zig-analyzer check .            # exits nonzero while findings remain
zig-analyzer check --fix .      # applies only provably safe rewrites
zig-analyzer check --no-cache . # reanalyzes files with cached findings
zig-analyzer check --strict-config .            # a configuration error stops the check
zig-analyzer check --write-baseline base.json . # records the current findings
zig-analyzer check --baseline base.json .       # reports only findings not recorded
zig-analyzer check --format sarif . > zig-analyzer.sarif # a report for code scanning
zig-analyzer check --rule missing-errdefer .    # reports only the rules named
zig-analyzer check --fail-on warning .          # fails only for warnings and errors
zig-analyzer explain missing-errdefer           # prints a rule's documentation
```

Findings for unchanged files are cached between runs; `--no-cache` forces a
full reanalysis. Imported deprecation warnings always use the current dependency
source. In the editor, edits and closes also refresh warnings in open importers.

The default [`deprecated-declaration`](rules/deprecated-declaration.md)
warning follows local declarations, literal file imports, and the standard
library. It skips named build modules whose compilation bindings are unresolved.

## Rules, tiers, and profiles

Every rule has a stable kebab-case code, such as
`missing-errdefer` or `discarded-error`, used consistently in configuration,
diagnostics, and suppression directives. The full index, with one document
per rule explaining why it exists and when it fires, is
[`docs/rules/README.md`](rules/README.md). `zig-analyzer explain <rule>`
prints a rule's page, with its tier, profile, default level and fixes, and
`zig-analyzer explain` lists every rule code by tier.

Every rule belongs to one of three tiers:

- **Semantic** diagnostics, such as unresolved calls and missing switch
  prongs, report code that cannot mean what it says. They are always on and
  cannot be configured.
- **Correctness** rules report valid-but-dangerous code and default to
  `warning`.
- **Style** rules are off by default and are enabled through a profile or
  per-rule configuration.

A profile enables a curated set of style rules at `information`;
`lints.profile` takes one name or an array of them, such as
`["strict", "modernize"]`:

- `official`, `idiomatic`, and `strict` progressively add style guidance.
- `modernize` targets migrations between pinned Zig releases.
- `disciplined` enables the bounded-loop, allocation, recursion, assertion,
  and function-size policies as an independent set. They hold production
  code only: `test` blocks are exempt, and so are tests, fixtures, fuzzers,
  and scripts (see below).

Style rules that belong to no profile (`line-length`, `todo-comment`, the
subjective `prefer-*` rewrites, and others) are enabled only by name.

### Per-path relaxations

Both the CLI and the language server judge each file by its path inside the
project, the directory holding `zig-analyzer.json`:

- Tests are `*_test.zig` and `*_tests.zig` files and the `test/`, `tests/` and
  `testing/` directories; fixtures, the inputs tests read, are the
  `fixtures/`, `fixture/`, `testdata/` and `test_data/` directories. Both may
  print (`prefer-log-over-print`), publish no API (`public-declaration-docs`),
  and skip `line-length`, `unused-private-declaration` and
  `literal-boolean-argument`: assertions and expected values make long lines
  that read worse wrapped, declarations exist to be inspected by a harness
  rather than called, and a literal `true` or `false` in a table of cases is
  the expected outcome rather than a hidden flag. A `testing/` directory
  outside `test/` and `tests/` may be a library's testing API (`std.testing`),
  so it keeps these three rules and its documentation rule. Naming rules and
  every correctness rule hold in tests and fixtures alike.
- Fuzzers (a path component containing `fuzz`) and scripts (`build.zig` and
  the `build/`, `scripts/` and `tools/` directories) publish no API either;
  `build.zig` may print, and its declarations stay documented because
  dependent build scripts import them.
- Tests, fixtures, fuzzers and scripts are exempt from the `disciplined` rules.
- A file whose leading comments say a tool generated it (`@generated`,
  `DO NOT EDIT`, Go's `Code generated ... DO NOT EDIT.`, a line starting
  `Autogenerated`, `Auto-generated` or `Generated by`, or `This file is
  generated` and its variants, within the first 16 lines and before any code)
  keeps its correctness and semantic findings, which the generator can be
  fixed for, but no style findings. Translate-c output is skipped entirely.

`overrides` (below) apply after these relaxations, so they can turn a relaxed
rule back on for some paths.

## Configuration

Configuration is read from the nearest `zig-analyzer.json` at or above the
directory being checked (for the CLI) or above each open file (for the language
server); both apply the same per-path relaxations and overrides, judged by the
path inside the project. The language server notices edits to the file on the
next request. Configuration errors are reported with the offending key rather
than silently ignored, once per change; an unknown key or rule name comes with
the nearest valid one. A malformed value stops reading the file there, while
an unknown key leaves the rest of the file in effect. `check` counts a
configuration error as a finding; with `--strict-config` it prints the error
and exits with status 2 without analyzing anything.

```json
{
  "check": {
    "exclude": ["zig-out", "vendor"]
  },
  "lints": {
    "profile": "idiomatic",
    "style": "warning",
    "rules": {
      "discarded-error": "warning",
      "line-length": { "level": "warning", "max-columns": 100 },
      "todo-comment": { "level": "hint", "markers": ["TODO", "FIXME"] }
    },
    "banned": [
      { "path": "std.BoundedArray", "hint": "use stdx.BoundedArrayType" }
    ]
  },
  "overrides": [
    { "paths": ["tests/**"], "lints": { "style": "off" } },
    {
      "paths": ["src/core", "src/**/*_unsafe.zig"],
      "lints": { "profile": "disciplined", "correctness": "error" }
    }
  ]
}
```

- `check.exclude` lists paths, relative to the project root, that
  `zig-analyzer check` skips. Keep exclusions narrow; exact files are
  appropriate for intentionally invalid parser, formatter, or
  syntax-highlighting fixtures.
- `lints.profile` selects one of the five named profiles, or an array of them.
- `lints.correctness` and `lints.style` set the level of the tier's selected
  rules: the correctness rules, which are on by default, and the style rules
  of the selected profiles. A tier setting never turns on a rule outside them,
  so `"style": "warning"` without a profile changes nothing; style rules of
  other profiles, profile-less style rules, and rules that require a project
  contract or compiler-backed project facts stay off until they are named.
- `overrides` changes the configuration of the files a pattern in `paths`
  matches, after the built-in per-path relaxations, in order (a later entry
  wins). Its `lints` takes `profile`, `correctness`, `style` and `rules` as
  above, applied on top of the file's configuration: profiles first, then
  tiers (whose selection includes the override's profiles), then rules by
  name. Patterns are relative to the project root; `*` matches within one
  path component, `?` one character, and a `**` component any number of
  components. A pattern names a path and everything below it, as
  `check.exclude` entries do, which also accept these patterns.
- `lints.rules` sets individual rules to `off`, `hint`, `information`,
  `warning`, or `error`. A rule with settings of its own takes an object with
  a `level` and its specific options, as `line-length` and `todo-comment`
  show above.
- `lints.banned` reports any use of the listed dotted identifier paths,
  with an optional hint naming the preferred alternative.

## Project contracts

Contracts extend the built-in analyses with project-specific facts, so the
strongest proofs apply to your own APIs without heuristics:

```json
{
  "contracts": {
    "imports": [{ "from": "src/rules", "deny": ["src/lsp", "src/compiler"] }],
    "resources": [{ "acquire": "Db.open", "release": "Db.close" }],
    "arena-allocators": ["RequestContext.allocator"],
    "must-use": ["Builder.finish"]
  }
}
```

- `imports` declares module boundaries: files under `from` may not import the
  denied paths.
- `resources` pairs an acquiring call with its releasing call, so the
  resource-lifecycle analysis and the cleanup rules (`missing-resource-cleanup`,
  `discarded-resource`, `resource-cleanup-on-error-only`,
  `cleanup-after-fallible-operation`, `returning-released-value`) treat your own
  APIs like `openFile`/`close`. A qualified entry such as `Db.open` only matches
  calls on that receiver.
- `arena-allocators` names allocator fields by their owner type, or allocator
  parameters by their function. For example, `RequestContext.allocator` and
  `render.allocator` declare that allocations made through those providers
  inherit a surrounding arena lifetime and do not require individual releases.
  Nested member paths such as `RequestContext.storage.allocator` are supported.
- `must-use` names functions whose return value must not be discarded.

## Cross-file analysis

The CLI builds conservative function summaries across direct calls.
Borrowing, release, escape, allocator provenance, and owned returns flow
across files; recursion, function pointers, ambiguous names, and unresolved
calls stay opaque rather than guessed at. A value retained by a container
before return is not treated as a second owned result. Opt-in compiler-backed
project rules compare public type shapes across analyzed build roots and report
public declarations outside every successfully analyzed root's import graph.

## Suppressing findings

An intentional finding is suppressed with a source directive:

```zig
// zig-analyzer: disable-next-line missing-errdefer
const buffer = try allocator.alloc(u8, 4);
```

The available forms are:

```zig
// zig-analyzer: disable-file discarded-error

operation() catch {}; // zig-analyzer: disable-line discarded-error

// zig-analyzer: disable discarded-error, needless-defer-block
operation() catch {};
defer { close(); }
// zig-analyzer: enable discarded-error, needless-defer-block
```

`disable-next-line` applies only to the following line. `disable` remains in
effect until the matching `enable`, and `disable-file` must appear before any
code. Directives accept comma-separated rule codes; omit the codes or use
`all` to target every rule. Malformed directives and unknown rule codes are
reported instead of being ignored. The
[`unused-suppression`](rules/unused-suppression.md) rule (in the `idiomatic`
profile) reports a named rule whose findings a directive never suppressed.

## Baselines

A baseline lets a project turn a rule on without fixing every existing
finding first. `check --write-baseline <file>` records every finding in a
JSON file and reports none of them; `check --baseline <file>` then reports
only findings the file does not record, and how many it covered. A finding is
recorded by its path relative to the project root, its rule, a fingerprint of
its line's text with whitespace normalized, and its position among the
findings in that file sharing those, not by line number, so edits elsewhere
keep it covered. Changing the line itself, or adding another identical
finding, reports it again. Configuration warnings and unreadable files are
never covered.

## Automatic fixes

`check --fix` and the fix-all source action in the editor apply only rewrites
that provably preserve semantics. Larger rewrites — converting a
`defer`-then-return sequence to `toOwnedSlice`, transferring cleanup from
`defer` to `errdefer`, collapsing `inline else`, replacing `orelse
unreachable` with `.?` — are offered as explicit code actions instead.

## Selecting rules and failing the check

`check --rule <code>` reports only the rules named; the option repeats and
takes comma-separated codes, and an unknown code stops the check with status
2 and the nearest code as a suggestion. It filters what is reported rather
than what runs: every enabled rule still runs, so findings that depend on the
others, such as [`unused-suppression`](rules/unused-suppression.md), stay the
same, and a rule the configuration turns off reports nothing. The findings of
other rules are not counted, recorded by `--write-baseline`, or fixed by
`--fix`. Configuration warnings and unreadable files are reported and counted
whatever `--rule` selects.

`check` exits with status 1 while findings remain, 2 for a usage error, an
unreadable path or baseline, or a configuration error under `--strict-config`,
and 0 otherwise. `--fail-on <level>` sets the least severe finding that fails
the check: `hint`, the default, fails on any finding; `information`,
`warning` and `error` ignore the levels below them; `never` always exits with
status 0 unless the check itself fails. Configuration warnings count as
`warning` and unreadable files as `error`. The report is the same at every
level.

## Report formats

`check --format <format>` chooses how the report is printed; every format
carries the findings of every pass, per-file, cross-file and project, after
`--rule` and any baseline. Whatever stops the check with status 2 goes to
standard error in every format but `text`.

- `text`, the default: one `path:line:column: level[rule]: message` line per
  finding, then the summary lines.
- `json`: one JSON document. `findings` lists each finding's `path`
  (relative to `root`, the scanned directory), `rule`, `level`, `message`,
  1-based `start` and `end` (`line` and `column`; the end is the position
  after the finding), its `related` spans (each a `message`, `start` and
  `end`), and its `fix`: `"fix_all"` when `check --fix` applies it,
  `"quick_fix"` when only the editor offers it, or `null`. `notices` lists
  configuration warnings, unreadable files and skipped files (`kind`,
  `level`, `path`, `start`, `message`). `summary` holds `files_checked`,
  `findings` (the count the text report ends with, configuration warnings and
  unreadable files included), `files_changed` and `edits_applied` for
  `--fix`, `baseline_covered` and `baseline_recorded`. `version` changes when
  a field changes meaning.
- `sarif`: a [SARIF 2.1.0](https://docs.oasis-open.org/sarif/sarif/v2.1.0/sarif-v2.1.0.html)
  log for code scanning. Each rule that has a result is described in
  `tool.driver.rules` with its catalog summary and its page in this
  repository; levels map `error` to `error`, `warning` to `warning`, and
  `information` and `hint` to `note`. Artifact URIs are relative to the
  `SRCROOT` base, the scanned directory, and columns count Unicode code points
  (`columnKind: "unicodeCodePoints"`), as the text report's do. Configuration
  warnings become tool configuration notifications, and unreadable and
  skipped files tool execution notifications. GitHub code scanning reads
  relative URIs against the repository root, so check from there when
  uploading the log.
- `github`: a GitHub Actions workflow command per finding (`::error`,
  `::warning`, or `::notice` for `information` and `hint`) with its `file`,
  `line`, `endLine` and, for a finding on one line, `col` and `endColumn`,
  and the rule as its `title`; the summary lines follow. Values are escaped
  as the Actions toolkit escapes them. Paths are the text report's, so run
  the check from the workspace root. GitHub shows a limited number of
  annotations per step.
